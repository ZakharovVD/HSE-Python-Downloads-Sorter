# Архитектура

## Задача и границы

Консольное приложение на Python 3.12 и новее. Внешние библиотеки не нужны.
Пользователь выбирает папку и JSON-конфиг, сначала просматривает план,
затем подтверждает перемещения. Обрабатываются только файлы верхнего уровня.
Дубликаты ищутся также в непосредственном содержимом папок категорий.

Приложение не удаляет дубликаты, не разбирает произвольное дерево папок
и не следит за загрузками в фоне.

## Структура

```text
hse-python-downloads-sorter/
├── ARCHITECTURE.md
├── README.md
├── pyproject.toml
├── downloads_sorter/
│   ├── __init__.py
│   ├── __main__.py
│   ├── cli.py
│   ├── config.py
│   ├── models.py
│   ├── filesystem.py
│   ├── planner.py
│   ├── history.py
│   ├── service.py
│   ├── duplicates.py
│   └── rules.json
└── tests/
    ├── __init__.py
    ├── helpers.py
    ├── test_cli.py
    ├── test_config.py
    ├── test_duplicates.py
    ├── test_planner.py
    ├── test_recovery.py
    └── test_service.py
```

`cli.py` отвечает за аргументы, вывод, подтверждение и коды завершения.
`config.py` читает JSON и проверяет типы, расширения и безопасные имена папок.
`models.py` содержит небольшие dataclass для правил, снимка файла, плана
и результатов. В этих классах нет бизнес-логики.

`filesystem.py` содержит общие операции: проверку обычного файла без перехода
по символической ссылке, потоковое вычисление SHA-256, проверку путей
и перемещение без перезаписи. `planner.py` выбирает категории и свободные
имена. Он не изменяет файлы и не открывает историю.

`history.py` хранит журнал и блокирует одновременное изменение одной папки.
Класс `History` оправдан тем, что владеет соединениями SQLite и закрывает
их при выходе из контекстного менеджера. `service.py` связывает журнал
с файловыми операциями и выполняет сортировку, восстановление после сбоя
и отмену. `duplicates.py` группирует файлы по размеру и хешу.

Зависимости направлены от интерфейса к прикладным функциям, затем к моделям
и операциям с файловой системой. Модули не импортируют `cli.py`.

## Поток сортировки

1. CLI проверяет исходную папку и конфиг.
2. Команда `sort` блокирует папку и восстанавливает незавершённые записи
   до построения плана. Команда `plan` историю не открывает.
3. Планировщик получает список файлов и снимок каждого: устройство, inode,
   размер и время изменения в наносекундах.
4. Сначала проверяются ключевые слова, затем расширения. Внутри каждого
   этапа побеждает первая категория в конфиге.
5. Планировщик резервирует итоговые имена, учитывая существующие файлы
   и остальные строки плана. Составное расширение `.tar.gz` сохраняется.
6. CLI печатает план. Команда `plan` на этом заканчивается.
   Команда `sort` получает подтверждение, удерживая блокировку.
7. Перед каждой операцией повторно проверяются файл, папка назначения
   и свободное имя. Изменившийся после просмотра плана файл пропускается.
8. Вычисляется хеш, затем в журнале сохраняется намерение переместить файл.
9. Выполняется перемещение и фиксируется его результат.

Ошибки отдельных файлов попадают в итоговый отчёт. Если журнал недоступен,
новые перемещения не выполняются.

## Перемещение без перезаписи

Обычный `rename` в Unix может заменить существующий файл. Поэтому используется
`os.link`: для исходного файла создаётся второе имя, затем удаляется исходное.
Создание ссылки завершается ошибкой, если целевое имя занято. Содержимое
и метаданные не копируются, а большой файл перемещается быстро.

Если удаление исходного имени завершилось ошибкой, приложение пробует убрать
только что созданное второе имя, предварительно сверив inode обоих путей.
Если такой откат невозможен, сохранённое намерение остаётся в журнале.

Файлы и папки категорий проверяются на символические ссылки. Если файловая
система не поддерживает жёсткие ссылки или папка категории находится на другом
устройстве, операция сообщит об ошибке и сохранит исходный файл. Это явное
ограничение выбранного способа перемещения.

Между созданием второго имени и удалением первого процесс может завершиться.
В таком случае останутся два имени одного файла. Журнал позволяет определить
такое состояние и завершить операцию при следующем изменяющем запуске.

Приложение защищает от обычных изменений файлов между планом и выполнением.
Оно не предназначено для работы в папке, которую параллельно намеренно меняет
другой процесс: полностью исключить все гонки путей средствами переносимого
Python нельзя.

## Состояние и восстановление

Служебная папка `.sorter-state` находится внутри исходной папки.
В `history.sqlite3` находятся две таблицы:

- `runs`: идентификатор и время сортировки в UTC;
- `moves`: запуск, относительные пути, SHA-256 и состояние перемещения.

Возможные состояния записи: `pending`, `moved`, `undo_pending`, `undone`,
`failed`. Намерение `pending` или `undo_pending` сохраняется до изменения
файловой системы. Каждое изменение журнала фиксируется отдельно.

При следующей сортировке или отмене незавершённые записи сверяются с файлами.
Если оба имени указывают на один inode с ожидаемым содержимым, операция
завершается. Если сохранилось только исходное имя, операция считается
невыполненной. Если сохранилось только целевое — выполненной.
Неоднозначное состояние блокирует новые изменения с понятным сообщением;
чужие файлы не удаляются для автоматического разрешения конфликта.

Для блокировки используется отдельный `lock.sqlite3` с открытой эксклюзивной
транзакцией. Он нужен отдельно, чтобы записи истории можно было фиксировать,
не отпуская блокировку всей операции. SQLite освобождает блокировку при
завершении процесса, поэтому не требуется вручную удалять устаревший lock-файл.

SQLite обеспечивает атомарность записей журнала. Файловая операция и запись
в БД не являются одной транзакцией, поэтому между ними нужен описанный журнал
намерений. Это восстановление после прерывания процесса, а не замена резервной
копии при физическом отказе диска.

## Отмена

Выбирается последний запуск с ещё не отменёнными перемещениями. Перед возвратом
проверяются контрольная сумма, отсутствие символических ссылок и свободное
исходное имя. Изменённый файл или конфликт пропускаются с сообщением.
Статус `undo_pending` сохраняется до возврата, `undone` — после.

Частичную отмену можно повторить: уже возвращённые файлы не затрагиваются.
После полной отмены следующий вызов `undo` переходит к предыдущему запуску.
Пустые папки категорий остаются на месте.

## Дубликаты

Сначала сравниваются размеры, затем только в группах из двух и более файлов
считается SHA-256. Чтение идёт блоками по 1 МиБ. Снимок файла сравнивается
до и после чтения, чтобы изменение во время вычисления не считалось
достоверным совпадением. Выводятся группы совпадений, файлы не удаляются.

## Интерфейс и ошибки

Команды: `plan`, `sort`, `undo`, `duplicates`, `history`. У каждой есть
`--source`; у команд с правилами есть `--config`. Для автоматизации `sort`
и `undo` поддерживают явный `--yes`. Без него требуется ответ `да` или `yes`.

Коды завершения: `0` — успех или отмена пользователем, `1` — ошибка запуска
или частичная ошибка обработки, `2` — неверные аргументы, `130` — прерывание.
Нормальный пропуск папки, скрытого или недокачанного файла ошибкой не считается.

Пользовательские ошибки выводятся без traceback. Перехватываются конкретные
ошибки конфигурации, файловой системы и SQLite. Неожиданные ошибки
программирования не маскируются универсальным `except Exception`.

## Проверка реализации

Автоматические тесты находятся в `tests/` и используют стандартный `unittest`.
Общий класс в `helpers.py` создаёт временную папку и небольшие настройки
для каждого теста. `test_cli.py` запускает приложение через `subprocess`,
остальные модули проверяют поведение соответствующих частей программы.

Проверки выполняются в изолированных временных папках: план без изменений,
приоритет ключевых слов, конфликты, повторный запуск, отмена, изменение файла,
неверный конфиг, символические ссылки, дубликаты и восстановление журнала.
Личные загрузки не используются для автоматической проверки.
